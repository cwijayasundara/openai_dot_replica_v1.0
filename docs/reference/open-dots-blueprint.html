Rebuilding OpenAI's dots on LangGraph, Deep Agents and Fireworks

What OpenAI shipped on 29 September, what it is made of, and how to build an open equivalent with Kimi K3 and GLM-5.3 on Fireworks.

Prepared for CK · stack: langchain 1.x · langgraph · deepagents ≥0.6 · Fireworks serverless

What Dots is

Dots are always-on agents that OpenAI launched at DevDay on 29 September 2026. They run on GPT-6 Astra. Each dot has its own cloud computer and browser, connects to 4,000+ apps, and can be reached from ChatGPT, Slack and Teams, with texting coming soon. You give it tasks and ideas in one ongoing conversation instead of separate threads. It works around the clock, researches in the background, and learns your preferences from feedback.

The product is mostly a harness, not a new model. Almost everything OpenAI describes is orchestration: a persistent agent identity, a sandboxed computer, channel adapters, a task queue, memory, a scheduler for proactive work, and a safety reviewer that sits in front of every consequential action. All of these can be built from open parts. The model is the one piece you swap.

Launch facts. Pro, Business Premium and Enterprise (incl. Edu/Healthcare) in eligible markets. One dot included per plan; more dots, speed and monthly work allowance to be sold later. Specialist dots for enterprises get their own identity, credentials and system access, with Microsoft Agent 365 governance. OpenAI held back GPT-6.1 Astra because it "didn't quite meet the bar of staying within scope and authorization" (CBS).

Model strategy on Fireworks

Don't run everything on one model. Dots is a mix of long-horizon planning, cheap always-on polling, and fast review calls, and the three current Fireworks options fit those roles well.

Things that will bite you

  • Reasoning history. Fireworks notes Kimi K3 is sensitive to thinking-history preservation. If reasoning content is dropped between tool turns, long runs degrade. A past langchain-fireworks bug (issue #34342) did not surface reasoning_content. Pin a current version and assert it round-trips in a test before anything else.
  • Prompt caching is your cost model. Cached input is 10× cheaper on Kimi K3 and about 5× on GLM-5.3. Keep the system prompt, tool schemas, AGENTS.md and skills index as a stable prefix, and put volatile content at the end.
  • GLM-5.3 is text-only. Browse with the accessibility tree / DOM when it's the operator; route screenshot tasks to Kimi K3 or Flash.
  • Tune the harness per model. Deep Agents 0.6 added harness profiles for this. Tool descriptions and the todo prompt that work on one model often need rewording for another; test per model rather than assume.
  • Data residency. Fireworks serves both models with zero data retention by default and has US-only tiers. Check EU requirements for UK/EU clients.

Code skeleton

A minimal but complete shape. Parameter names follow the current Deep Agents docs; confirm backend constructor signatures and the async-subagent spec class against your installed version, since both have moved between releases.

1. Models

from langchain_fireworks import ChatFireworks

FW = "accounts/fireworks/models/"
supervisor = ChatFireworks(model=FW + "glm-5p3", temperature=0.2, max_tokens=8192)
heavy      = ChatFireworks(model=FW + "kimi-k3", temperature=0.2, max_tokens=16384)
fast       = ChatFireworks(model=FW + "glm-5p3-flash", temperature=0)
# Equivalent string form: init_chat_model("fireworks:accounts/fireworks/models/glm-5p3")

2. Guardian middleware (primitives 8–10)

from langchain.agents.middleware import AgentMiddleware
from langchain_core.messages import ToolMessage
from pydantic import BaseModel

# allow | approve | block, set per dot by the user (Dots' "custom rules")
POLICY = {
    "read_*": "allow", "search_*": "allow", "draft_email": "allow",
    "send_email": "approve", "create_pr": "approve", "pay_invoice": "approve",
    "change_password": "block", "delete_repo": "block",
}

class Verdict(BaseModel):
    in_scope: bool          # does this match what the user asked for?
    risk: str               # low | medium | high
    reason: str

reviewer = fast.with_structured_output(Verdict)

class Guardian(AgentMiddleware):
    def wrap_tool_call(self, request, handler):
        name = request.tool_call["name"]
        rule = match_policy(POLICY, name)            # glob match, default "approve"
        if rule == "block":
            return ToolMessage(f"Blocked by policy: {name}", tool_call_id=request.tool_call["id"])
        if rule == "allow" and is_read_only(name):
            return handler(request)
        v = reviewer.invoke(guardian_prompt(request.state, request.tool_call))
        audit_log(name, rule, v)
        if not v.in_scope or v.risk == "high":
            return ToolMessage(f"Guardian refused: {v.reason}", tool_call_id=request.tool_call["id"])
        return handler(request)   # "approve" tools are paused by interrupt_on (below)

3. The dot (primitives 1–3, 7)

from deepagents import create_deep_agent
from deepagents.backends import CompositeBackend, StoreBackend
from deepagents.backends.sandbox import DaytonaSandbox   # or Modal / Runloop

approve = {"allowed_decisions": ["approve", "edit", "reject"]}

dot = create_deep_agent(
    model=supervisor,
    system_prompt=DOT_PERSONA,              # name, tone, standing goals
    tools=mcp_tools + composio_tools,       # primitive 5
    memory=["/memories/AGENTS.md"],         # learned preferences
    skills=["/memories/skills/"],           # learned procedures
    backend=lambda rt: CompositeBackend(
        default=DaytonaSandbox(rt, snapshot="dot-base"),   # the dot's computer
        routes={"/memories/": StoreBackend(rt)},           # durable across threads
    ),
    subagents=[
        {"name": "coder", "model": heavy, "description": "Code changes, tests, PRs",
         "system_prompt": CODER_PROMPT, "tools": git_tools},
        {"name": "researcher", "model": supervisor, "description": "Web and doc research",
         "system_prompt": RESEARCH_PROMPT, "tools": search_tools},
    ],
    # Long jobs run as async subagents on Agent Protocol endpoints so the dot keeps
    # answering new messages. Add them per your deepagents version's async spec.
    interrupt_on={t: approve for t in tools_with_rule(POLICY, "approve")},
    permissions=[{"path": "/memories/**", "allow": ["read"], "deny": ["delete"]}],
    middleware=[Guardian()],
    checkpointer=postgres_checkpointer, store=postgres_store,
)

4. Channel router (primitive 4)

from langgraph_sdk import get_client
lg = get_client(url=LANGGRAPH_URL)

async def on_message(user_id: str, channel: str, text: str, reply_to):
    thread_id = dot_thread_for(user_id)          # ONE thread per dot, all channels
    await lg.runs.create(
        thread_id, assistant_id="dot",
        input={"messages": [{"role": "user", "content": f"[{channel}] {text}"}]},
        multitask_strategy="enqueue",             # never drop a message mid-run
        webhook=reply_url(channel, reply_to),
    )
# Interrupts from interrupt_on surface as approve / edit / reject buttons in the same channel.

5. Proactive sweep (primitive 6)

sweeper = create_deep_agent(
    model=fast, tools=read_only_tools,           # hard read-only, not just "please don't"
    system_prompt=SWEEP_PROMPT,                  # watchlist from /memories/goals.md
    backend=lambda rt: CompositeBackend(default=StoreBackend(rt), routes={}),
)
await lg.crons.create_for_thread(
    dot_thread_for(user_id), assistant_id="sweeper",
    schedule="*/30 7-22 * * *",                  # waking hours; keep nights cheap
    input={"messages": [{"role": "user", "content": "Run your sweep."}]},
)
# Findings are written to an inbox; the dot decides whether they are worth your attention.

Guardian and permissions, in more detail

OpenAI's safety design is the part most worth copying exactly, because it is what makes an always-on agent tolerable. Their stated defaults: draft instead of send, no financial transactions without confirmation, read-only for background work, credential changes never delegated.

  • Two separate checks. A deterministic policy table runs first and is the source of truth. The reviewer model only adds an "is this in scope of what the user asked?" check on top. Never let the LLM reviewer loosen a rule.
  • Use a different model for review. Flash reviewing GLM-5.3 or Kimi K3 actions avoids the same model rationalising its own plan. Give it the original user instruction, the action, and the dot's standing rules, and nothing the tool returned from the web, which is where prompt injection comes from.
  • Tag tools by effect, not by name. Each tool declares effect: read | write | external | financial | credential. Policies attach to effects, so a newly added MCP server inherits sane defaults.
  • Specialist dots need their own identity. A procurement dot gets its own service principal and scoped credentials, not the user's. This is the Agent 365 point in OpenAI's launch.
  • Everything is auditable. Every tool call, Guardian verdict and approval goes to LangSmith traces plus an append-only audit table the user can view, which is the equivalent of watching the dot's computer.

The learning loop

"Learns from feedback over time" without fine-tuning is the same problem as your RSI work: the model stays fixed and the harness evolves from memory. A practical version for a dot:

  1. Capture. Every approve, edit, reject and explicit correction is an episode in the Store: the task, what the dot proposed, what the user did instead.
  2. Reflect nightly. A job clusters the day's episodes and proposes edits to /memories/AGENTS.md (preferences, standards) and to skills (procedures that recurred three or more times).
  3. Gate the change. Replay a small set of stored episodes against the edited harness and keep the edit only if approval rate or edit distance improves. Show the diff to the user once a week.
  4. Keep it reversible. Version the memory files so a bad lesson can be rolled back.

This is also where the "packs" idea from your config-driven platform fits: a specialist dot is a pack (persona, skills, tools, policy table, sweep schedule), and the learning loop edits the user's copy of that pack.

Cost envelope per dot

Illustrative only, using Fireworks list prices above and these assumptions: 20 substantive tasks a day at 300k input (70% cached) and 20k output each; a proactive sweep every 30 minutes (48/day) at 50k input (80% cached) and 2k output; 200 Guardian reviews a day at 8k input and 300 output, uncached.

A sensible mix (GLM-5.3 by default, Kimi K3 for the hardest quarter of tasks) lands around $200–230 a month of inference per heavily used dot, before sandbox compute. Sandbox time, not tokens, is often the bigger line for an always-on computer, so suspend sandboxes between tasks and restore from a snapshot.

Build plan

Weeks 1–2

Single-channel dot. Supervisor on GLM-5.3, sandbox backend, Store memory, Slack adapter, one thread per dot. Test reasoning-content round-trip on both models first.

Weeks 3–4

Safety layer. Effect-tagged tools, policy table, Guardian middleware, interrupt-based approvals rendered as Slack buttons, audit log.

Weeks 5–6

Always-on. Async subagents for coder and browser operator on Kimi K3, enqueue multitasking, read-only proactive sweeps on cron with a findings inbox.

Weeks 7–8

Learning and reach. Episode capture, nightly reflection with replay gating, Teams and SMS adapters, Composio or Arcade for connector breadth.

Weeks 9+

Specialist dots and voice. Packaged specialist dots with their own identities; LiveKit voice front end reusing the same thread.

Recommendation

Build it as a harness on Deep Agents, with GLM-5.3 as the supervisor, Kimi K3 behind async subagents for hard work, and GLM-5.3-Flash for Guardian and sweeps. Spend your first real effort on the one-thread-per-dot runtime and the Guardian, because those are what make Dots different from a chat agent. Treat the learning loop as a direct application of your RSI research rather than a separate feature.
