Open Dot: an always-on agent you can host yourself

How our replica of OpenAI's dots is built, where it follows the original, where it differs, and why it is a different kind of system from the chat agents most teams build today.

Written 2 Oct 2026 Stack: deepagents 0.7.20 · LangGraph 1.2 · LangChain 1.4 · Postgres 17 · Fireworks Sources: docs/design.md, the feature docs in docs/, src/dot/

01What a dot is

A dot is an agent that keeps living after the conversation ends. It has one identity, one memory of everything you have asked it, and its own computer. It works when you are not watching, and it asks before it does anything that matters.

OpenAI launched dots at DevDay on 29 September 2026: always-on agents on GPT-6 Astra, each with its own cloud computer and browser, reachable from ChatGPT, Slack and Teams in one ongoing conversation, doing background research and learning from feedback. Almost everything they described is orchestration rather than model. That is what makes an open equivalent possible: the harness can be rebuilt from open parts, and the model is the one component you swap.

Our replica reduces the idea to one sentence that runs through the whole codebase:

PackDeclarative YAML: persona, skills, wiki, tools, policy, profiles, schedules and subagents. Validated by pydantic at load time.
+
ThreadOne LangGraph thread for the life of the dot, checkpointed in Postgres and shared by every channel.
+
ComputerA sandbox behind the execute tool, started on first use, suspended when idle. Docker or OpenShell.

On top of that core sit the parts that make it safe to leave running: effect-tagged tools, a deterministic policy table, an independent Guardian reviewer, human approval cards, an append-only audit log, a credential broker the model never sees past, read-only proactive sweeps, durable background jobs, and a learning loop that edits memory only when replay shows the edit does no harm.

The governing rule. Agents propose, code decides, humans approve. Policy, gates, approvals, budgets and credential resolution are code. No prompt is ever the only thing enforcing a rule. Every design choice below follows from this.

The short version

Versus a normal agent
  • A normal agent is a function call. A dot is a process with a lifetime, a queue and a computer.
  • A normal agent trusts the model to behave. A dot assumes the model will sometimes be wrong or manipulated, and puts code between it and every side effect.
  • A normal agent forgets. A dot accumulates memory, but only through a gate.
Versus OpenAI's dots
  • Same ten primitives, mapped to open components. The safety design follows OpenAI's stated defaults closely: drafts not sends, read-only background work, credential changes never delegated.
  • We trade model quality and connector breadth for ownership: you host it, read every line of policy, and swap models per role.
  • No browser or computer-use operator, no voice or SMS, no Teams yet.

One assembly

src/dot/assembly.py builds models, tools, middleware and agents for the API, worker, CLI, replay and tests. There is no per-surface fork. build_dot_agent builds the supervisor for a given profile; build_job_agent builds a background job with the same chain; replay calls build_dot_agent again with a scratch runtime. A rule added once applies everywhere, and a test of the assembly is a test of production.

04Life of a message

A Slack DM that asks the dot to research a topic and email a brief to a colleague.

  1. Inbound. Slack verifies the sender. The router maps the Slack user to the owner and the owner to their dot. Bot posts and redeliveries are ignored; each (channel, ts) is accepted once. An inbox row is written with source slack and a reply reference.
  2. Claim. The worker claims the row with FOR UPDATE SKIP LOCKED and takes the dot's advisory lock. If a turn is already running, the message waits and joins the next turn.
  3. Build. Assembly builds the supervisor for the chat profile: persona, tools the profile grants, subagents, memory and skills reloaded from the store, middleware chain, Postgres checkpointer.
  4. Capture the objective. Guardian middleware records the trailing human messages as the turn's original instruction. This, not anything the model writes later, is what consequential actions are judged against.
  5. Research. The supervisor delegates to the researcher subagent (web_search, fetch_url; both read). Fetched content is wrapped as untrusted data. Large results are offloaded to artifacts; tools return compact JSON plus artifact ids.
  6. Draft. draft_email is a draft effect: allowed, reviewed by the Guardian, runs.
  7. Send is gated. send_email is approve. The Guardian reviews first; if it refuses, the human is never asked. If it permits, LangGraph interrupts, the worker persists an approval card and marks the dot paused.
  8. Human decision. The card appears in the same Slack thread and in the web UI. An approver clicks Approve, Edit or Reject. The decision and an episode are committed atomically, plus one internal resume row.
  9. Resume. Only the worker resumes, after checking thread, profile, checkpoint and interrupt set. An edited call goes back through guard, policy and Guardian before it runs. The SMTP password is resolved from cred:smtp inside the tool.
  10. Reply and record. The reply goes to the outbox and is posted in order to the originating Slack thread. Every step is in the audit log, viewable per turn.

05The safety layer

The deterministic layers decide. The model reviewer can only add refusals, never grant. Humans approve what policy says needs approval.

Effect-tagged tools

Every tool registers exactly one effect. Policies attach to effects, so a new tool inherits sane defaults without anyone writing a rule for it. Unknown and untagged tools are always blocked, even if a name rule would match them. An MCP tool without an effect in config/mcp.yaml is never offered.

EffectMeaningDefaultExamples
readNo side effect outside the dotallowweb_search, fetch_url, record_finding, job tools, task
draftProduces something for a human to useallow + Guardiandraft_email, write_report
writeChanges state the org ownsapprovesandbox write_file, edit_file, execute; start_run
externalSends or publishes outside the orgapprovesend_email, slack_post
financialMoves moneyapprovenone shipped
credentialTouches secrets or accessblocknever delegated

Policy table

defaults: {read: allow, draft: allow, write: approve, external: approve, financial: approve, credential: block}
tools:
  send_email: approve
  delete_*: block          # first matching glob in YAML order wins; else the effect default
approvers: []              # nobody can approve until configured; owning a dot is not approval access

Assembly snapshots policy and registry effects when it compiles an agent, so later mutation cannot change a running agent's decisions. A pack whose profile grants an effect the policy blocks fails to load.

The middleware chain, in execution order

This is the real order from assembly._chain. Note one deliberate difference from the design sketch: human review wraps the outside. LangChain's HITL middleware substitutes reviewer edits inside its wrapper, so the guards must sit inside it to see the edited call. A reviewer cannot redirect an allowed call into a blocked or hidden tool.

01
HumanInTheLoopMiddleware

Interrupts on approve tools. The map holds only concrete tools this agent was offered; its when hook asks the Guardian first, so a refused call never reaches a human.

02
AuditMiddleware

Records proposals, attempts, results and errors. A storage failure before a tool call prevents the call.

03
SurfaceGuard

Filters tools by the active capability profile and refuses calls to tools the model was not shown. Ported from recon v2's invocation guard.

04
OffloadMiddleware

Large tool results become artifacts; the model gets a preview and an id.

05
RedactionMiddleware

Scrubs every resolved secret from messages, tool args, reasoning metadata and artifacts, including JSON-escaped forms.

06
PolicyMiddleware

Returns an error ToolMessage for block; the tool never runs. Checked at proposal and again before execution.

07
GuardianMiddleware

Reviews permitted calls with effects above read. Captures the turn's instruction. Caches verdicts in graph state keyed by instruction and exact call; an edited call is reviewed again.

08
ModelRetryMiddleware

Retries model failures. Jobs and replay fail hard, so a model error is never reported as a result.

09
ModelCallLimit or Budget

Per-run call ceiling; schedules use a shared model-call and token budget instead.

The Guardian

A structured reviewer on the fast model returning an immutable Verdict{in_scope, risk, reason}. Code permits a call only when it is in scope and risk is not high. Exceptions, malformed verdicts and a missing instruction all become refusals.

  • What it sees: a fixed reviewer prompt, the original user instruction, the pending tool name and arguments, its effect, and the policy summary.
  • What it never sees: conversation history, tool messages, fetched documents, assistant reasoning, or a subagent's model-written task description. Prompt injection arrives through fetched content; the reviewer is kept away from it.
  • Whose objective: for a background job, the user's instruction recorded in code when the job started, never the instructions the supervisor wrote for it. For a sweep or digest, the schedule's prompt, never the findings' text.
  • Evidence: a live gate of 20 labelled cases (10 permissible, 10 refusals) needs 18/20. glm-5p3-flash scored 20/20 on two runs on 1 Oct 2026.

Approvals

Interrupts become approval cards with deterministic ids, so replaying persistence never duplicates them. POST /approvals/{id} takes approve, edit (new arguments, same tool) or reject. The caller's identity comes only from trusted middleware; anyone not in the pack's approvers gets 403. The API returns 202 after recording the decision, not after running the tool: approval is not proof of success. Concurrent or duplicate decisions get 409. Failed executions are not retried automatically, because external side effects are not guaranteed idempotent.

Credentials and redaction

The model works with handles. The broker accepts only administrator-configured handles and never derives an environment name or secret path from a model argument. Secret Manager payloads are CRC32C-checked. Transport exceptions become generic messages so provider errors cannot echo a password. The sandbox receives no credentials; when it needs to reach an API, OpenShell's L7 policy allows specific read-only requests.

Prompt-injection posture

  • Fetched and tool-returned content is wrapped as untrusted data with a marker the persona explains.
  • Research subagents have no write, external or financial tools.
  • fetch_url resolves hostnames and refuses any non-public address (so metadata.google.internal is out), follows no redirects, caps bodies at 1 MB.
  • Job output never arrives as an inbound message, only through check_job as an untrusted excerpt.
  • Slack output is escaped and posted with unfurls off, so injected <!channel> and disguised links are inert.

06Background jobs

How the dot keeps answering while it works. Deep Agents' async subagents target Agent Protocol servers, which we do not run, so we provide the same five tools over a Postgres jobs table.

ToolBehaviour
start_job(subagent, instructions)Returns a job_id at once. Only subagents granted to this turn's profile. The job's origin (channel, inbox ids, the user's instruction) is filled from graph state, never from arguments.
check_job(job_id)Status, last update, result_ref; once done, the result as an untrusted 4,000-character excerpt.
update_job(job_id, message)Appends an instruction the job reads before its next model call.
cancel_job(job_id)Stops within one step: the next tool call returns an error and does not run.
list_jobs(status?)The latest 20 of this dot's jobs. Another dot's job is "no such job".

A job is its own Deep Agent on its own thread ({dot thread}:{job_id}) with the subagent's model, tools and the full middleware chain; a sandboxed job gets its own sandbox key. A claim is an advisory lock held for the whole run, so a job whose worker died is picked up and resumed from its checkpoint. On finish, the result is stored as an artifact and a job_result row is written to the dot's inbox in the same transaction; the dot then reports back in the channel the request came from.

A job that hits an approval pauses rather than fails. Its sandbox is suspended, not closed, and the dot itself keeps answering. Cancelling a paused job closes its pending cards.

07The computer

A pluggable seam, RunSandbox(BaseSandbox), ported from recon v2. Agent code does not know which backend it runs on.

default · local and CI
Docker

network none, read-only root, tmpfs /work, cap_drop ALL, no environment. Snapshot and restore of /work.

local · GCP via GCE VM
OpenShell 0.1.2

Inputs and skills sealed into a root-owned image layer. Landlock required. Default policy denies egress; a research profile allows curl GETs to an allowlist. Denials are audited.

later
Cloud Run / GKE

Fresh no-network runs carrying /work as a tar; stateful gVisor sandboxes with warm pools.

Every backend has the same layout: /in read-only inputs, /skills read-only, /work writable. A LazySandbox starts only on first use, so a conversation that never calls execute never pays for a container. The coder subagent on Kimi K3 gets only execute and file tools, and its file middleware talks to the sandbox directly, so it cannot reach the supervisor's memory routes. Under the default policy every sandbox write and every execute needs approval.

Live acceptance on 1 Oct 2026: the coder computes a CSV summary with Kimi K3 under Docker (about 130 s) and under a local OpenShell gateway (about 65 s).

08Proactivity

A dot acts without being asked, but its unsupervised work is read-only by construction, not by request.

KindThreadCan doLeavesTells you
sweepIts own, deleted afterread tools, record_finding, granted read-only subagentsFindingsNothing
digestThe dot's threadIts profile's toolsFindings marked reportedOne summary in the default channel
reflectionNone (learning lane)Runs no agentProposed memory editsDiffs in the Memory tab
  • A pack fails to load if a sweep's profile, or a subagent it grants, can reach any non-read tool. Sweeps get no job tools, because a job would escape the budget.
  • Each run has one model-call and token ceiling shared with its subagents. Overrunning ends the run silently and records a budget finding.
  • A firing is dropped while that schedule's last row is still pending, and a slot never runs twice. Cloud Scheduler's schedule-time header makes retries idempotent.
  • A pending approval pauses the dot's schedules. Missed slots are not caught up; open findings wait for the next digest.

09The learning loop

A dot gets better by editing its own memory, not its weights. The model proposes edits; replay and a fixed rule decide which are kept; a human can roll any of them back.

Episodes

Every approval decision writes an episode in the same transaction, pointing at the exact checkpoint that produced the proposal. Corrections ("Don't cc my manager") come only from an explicit "Correct this" action in the web UI or a Slack message shortcut. Code never guesses which chat messages are corrections. Correction text is untrusted data and never reaches a system prompt.

Reflection

One structured call to the fast model with the memory files and the episodes. The model returns find/replace edits, because models get unified-diff line numbers wrong; code builds the diff. Code then drops any edit that targets a path outside AGENTS.md, an existing skill or a wiki page, whose find is not unique, that cites episodes it was not given, that pushes a file past its cap, that contains a known secret, that breaks a skill's frontmatter, or that repeats an edit a human already rolled back.

The replay gate

For each proposed edit, replay rebuilds the agent with the same assembly on a scratch runtime (in-memory saver and store, no repositories, no network, a sandbox factory that raises), seeds it with the messages at the episode's checkpoint minus the original proposal, and runs until ReplayStop fires: the episode's tool is called, any non-read tool is called, or the model replies. Baseline and candidate arms run against the same state. An edit is kept only if the match rate does not fall and at least one episode improves.

Because a dot's thread never ends, deepagents' once-per-thread memory load would mean no edit ever took effect. middleware/memory.py replaces those middlewares with versions that reload AGENTS.md and skills at the start of every turn.

11Models and cost

Dots mix long-horizon planning, cheap always-on polling and fast review calls. One model for all three is either too expensive or too weak, so each role gets its own.

RoleFireworks modelIn / cached / out per 1MUsed for
supervisorGLM-5.3 glm-5p3$1.40 / $0.26 / $4.40The dot, researcher subagent, replay arms
heavyKimi K3 kimi-k3$3.00 / $0.30 / $15.00Coder subagent, long documents, vision
fastGLM-5.3-Flash glm-5p3-flash$0.15 / $0.03 / $0.50Guardian, sweeps, reflection drafts
  • One factory. Provider fireworks (ChatFireworks) or openai_compatible (ChatOpenAI with a base URL), per role.
  • Reasoning round-trip is a gate. Kimi K3 degrades if its reasoning history is dropped between tool turns, and an earlier langchain-fireworks bug did exactly that. A live test asserts it survives a three-tool loop.
  • Prompt caching is the cost model. Persona, tool schemas, AGENTS.md and the skills index form a stable prefix; volatile content goes last.
  • Envelope. The research estimate for a heavily used dot (GLM-5.3 by default, Kimi K3 for the hardest quarter) is about $200–230 a month of inference, before sandbox compute. Sweeps and Guardian reviews on Flash add roughly $13. Sandbox time is often the bigger line, which is why sandboxes are lazy and suspend when idle.

12Packs

A specialist dot is a pack. The same runtime runs both shipped packs without code changes.

packs/research-analyst
research-analyst

A generic dot that watches sources, researches, writes briefs and drafts messages. Tools: web_search, fetch_url, draft_email, send_email, slack_post, write_report. Subagents researcher and sandboxed coder. Sweep every 30 minutes in working hours, digest at 08:45, reflection at 02:00.

packs/onboarding-ops
onboarding-ops

Watches a drop folder and operates the recon workbench over HTTP. An intake sweep records new files; an intake digest proposes start_run, which always needs approval. The dot never answers a workbench gate. Status sweep hourly, daily digest at 06:45 drafts sponsor questions.

profiles:                         # capability profile per entry point
  chat:   {tools: "*", subagents: "*"}
  sweep:  {effects: [read], subagents: [researcher]}
  digest: {effects: [read, draft]}
schedules:
  - {name: sweep,  cron: "*/30 7-22 * * 1-5", profile: sweep,  max_model_calls: 15, max_tokens: 150000}
  - {name: digest, kind: digest, cron: "45 8 * * 1-5", profile: digest, max_model_calls: 6, max_tokens: 60000}
  - {name: reflection, kind: reflection, cron: "0 2 * * *"}

Load-time validation rejects an unknown tool, an untagged tool, a profile that grants an effect the policy blocks, a sweep that can reach a non-read tool, and a coder configured without a sandbox or with native tools.

Where we are ahead

  • Inspectable rules. Policy is a YAML file and a resolver you can read and test, not a product setting.
  • Gated learning. Memory edits are proven against past decisions before they land, and every one can be rolled back.
  • Ownership. Data, models and runtime stay in your infrastructure; each role's model can be swapped.
