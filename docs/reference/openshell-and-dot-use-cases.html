Where OpenShell fits, and which knowledge work suits a dot

An answer to two questions: can NVIDIA OpenShell replace the Deep Agents sandbox for local and GCP deployment, and which knowledge-work use cases fit a dots-style architecture. Grounded in your recon_knowledge_work_agent_v2 repo and LangChain's paid media agent.

Reviewed: recon_knowledge_work_agent_v2 (deepagents 0.7.19, langgraph 1.2, Docker + ACA sandboxes) · OpenShell alpha · open-paid-media-agent

Short answers

1. OpenShell: yes, but as the sandbox, not the agent runtime

OpenShell does not replace Deep Agents or LangGraph. It replaces the execution environment behind the execute tool, and adds policy-enforced egress, credential injection and audit around it. LangChain already ships a reference that does exactly this (openshell-deepagent, "swap ModalBackend → OpenShellBackend and everything else stays the same").

You also don't depend on any hosted Deep Agents sandbox today. Your repo already implements the sandbox protocol twice (DockerSandbox, AcaSessionSandbox, both subclasses of BaseSandbox). OpenShell would be a third implementation of that same seam.

On GCP: the agent and API run fine on Cloud Run. The OpenShell gateway does not, because it runs k3s inside Docker and Cloud Run doesn't allow that. Put the gateway on a GCE VM or GKE, or use Google's own Cloud Run sandboxes or GKE Agent Sandbox instead.

2. Dots fit continuous, multi-system work where the agent proposes and people approve

Your recon agent is a workbench: a bounded run with code gates that produces one artifact. A dot is the long-lived colleague that notices work arriving, starts workbench runs, chases missing inputs, reports, and learns each client's quirks. The pattern that scales is a dot on top with specialist workbenches underneath. Your code-owns-the-gates spine stays exactly as it is.

Runtime vs sandbox: three planes

It helps to separate three things that often get called "the runtime":

PlaneJobIn your repo todayWhere OpenShell sits
Control (the agent's brain)Model calls, planning, subagents, middleware, checkpoints, gatesDeep Agents + LangGraph spine in FastAPI, Postgres checkpointerNot here. Keep LangGraph
Execution (the agent's computer)Run code the model wrote, hold scratch filesRunSandbox: Docker locally, ACA dynamic sessions on AzureHere. A sandbox per run or per dot
Governance (the rules around it)What the computer can reach, which credentials it can use, auditDocker flags: network none, read-only root, cap_drop ALL; executor /sealHere. YAML policy, L7 proxy, credential placeholders, OCSF audit

For the recon agent, the governance you need is simple: no network and no secrets, and Docker flags already do that well. OpenShell becomes valuable when the agent's computer must reach real systems with real credentials. That is the dot case: pulling from a sponsor's SFTP, reading SharePoint, calling Intacct's API in read-only mode.

What OpenShell gives you

  • Four policy domains. Filesystem and process rules are fixed when the sandbox is created (Landlock, seccomp, unprivileged identity). Network and provider-credential rules hot-reload at runtime.
  • L7 egress control. The supervisor runs outside the workload and inspects HTTP method, path and GraphQL operation, so "read from this API, never write" is enforced below the model. Rules can also be bound to specific binaries.
  • Credential placeholders. The sandbox only holds placeholders. "The real credential is substituted outside the agent workload and only for an authorized endpoint." This is the infrastructure version of OpenAI's "passwords never reach the model".
  • Inference routing. Model traffic goes through policy-controlled routes to approved providers, which suits clients who restrict where prompts go (your repo already restricts runtime models to OpenAI).
  • Audit and policy advisor. Decisions are logged in OCSF format. When something is blocked, the agent gets a descriptive error and can propose a narrow policy change for human review.
  • Maturity. Apache 2.0, still alpha (0.1.0 "coming soon"), Kubernetes deployment experimental. The BlueField/Sentry monitoring layer in the blog post is NVIDIA hardware and optional. The software runtime works on Linux, Apple Silicon macOS and WSL 2.

Deploying on GCP

A layout that keeps Cloud Run for what it's good at:

  subgraph CR["Cloud Run"]

  end

  A --> GCS[("GCS: uploads, artifacts")]
  A -->|"recon jobs: no network"| S1["Cloud Run sandbox or GKE Agent Sandbox"]
  A -->|"dot jobs: needs SaaS access"| GW["OpenShell gateway on GKE or GCE"]
  GW --> S2["OpenShell sandbox"]
  S2 -->|"policy-checked, credential injected"| EXT["SharePoint, SFTP, Intacct read-only"]
  • Recon-style jobs (no network, no secrets): Cloud Run sandboxes are the least infrastructure, since they run inside the API's own instance at no extra cost. The catch is that each sandbox do is fresh, so your adapter has to export and import /work as a tar on each call. If that latency hurts the recipe engineer's loop, use GKE Agent Sandbox, which keeps a stateful pod per run and matches your Docker contract more closely.
  • Dot-style jobs (network plus credentials): OpenShell on GKE or a small GCE VM. This is where its policy and credential model earns its place.
  • Locally: keep Docker as the default. Add OpenShell as a second local backend so policies are written and tested on the laptop before they reach GCP.
  • This client: your repo targets Azure (Bicep, ACA, Azure OpenAI). The GCP layout above is for your other deployments. For this one, finish the ACA spike your code comment calls for.

        self._session = None

    def start(self) -> None:
        # create sandbox "onb-{run_id}" from the onb-sandbox image with self._policy,
        # copy /in, /ref and /skills, then seal them read-only (as the ACA executor does)
        ...

    def execute(self, command: str, *, timeout: int | None = None) -> ExecuteResponse:
        out = self._session.exec(command, timeout=timeout or DEFAULT_TIMEOUT_S)   # port from openshell-deepagent
        text, truncated = truncate(out.output)
        return ExecuteResponse(output=text, exit_code=out.exit_code, truncated=truncated)

    # upload_files / download_files: restrict writes to /work exactly like DockerSandbox

filesystem:

Add sandbox_backend = "openshell" to Settings and an openshell_sandbox_factory in assembly.py, next to the Docker and ACA factories. Nothing in the agents, tools or spine changes.

The point: a dot doesn't replace your workbench, it operates it. Paid media shows the middle ground, which is the right first step for enterprise knowledge work: scheduled cycles and chat follow-ups in one runtime, with human approval on every change.

A thin, always-on layer over the code you already have. The rule from your CLAUDE.md carries over unchanged: agents propose, code decides, humans approve. The dot can start runs and prepare evidence but can never pass a gate.

Lessons from the paid media agent

  • Model for judgment, code for computation. Their first version put raw data in context: 3.9M input tokens, 1,112 seconds and $3 per report. Moving calculations to Python made it 40× cheaper and 13× faster (18 minutes to 85 seconds). Your onboarding SDK already follows this rule; keep it for every new workbench.
  • Five context layers. System prompt as a map, skills for reusable method, a wiki for company-specific context, live tools for current data, and code for hard rules. Their test: "A skill should work at another company, whereas the wiki should not." Your skills folder is the first half; the per-sponsor wiki is the missing half.
  • One runtime, a capability profile per entry point. They began with two agents (scheduled and Slack) and merged them, so the agent can answer follow-ups in the thread that produced a report.
  • Tool discovery for large tool sets. Search, read schema, then run cut context from 38k to 12k tokens across 200+ tools. You'll need this once a dot has many connectors.
  • Isolation is explicit. "A subagent gives you a separate context window. The rest of the isolation model is up to you." Give each subagent its own output location, completion state and tool list.
  • Approval cards check who approves. Slack Block Kit cards show current against proposed values, and only authorised user ids can apply them. Your spine's approvers list is the same idea.
  • Results worth quoting to clients. Paid pipeline share went from 0 to 20% in six months, cost per lead fell 30%, and $5K a month of agency reporting was cut.

Next steps

Step 1

Add a third sandbox backend. Port OpenShellBackend into OpenShellSandbox(RunSandbox) with a deny-all policy and pass the existing sandbox contract tests. This settles the local question.

Step 2

Choose the GCP execution backend. Spike Cloud Run sandboxes with tar-carried /work against the recipe engineer's live eval. If wall time regresses noticeably, switch to GKE Agent Sandbox.

Step 3

Add the dot layer. A Deep Agents supervisor with three capability profiles (sweep, chat, digest), tools over Workbench (never respond), a Teams adapter and a per-sponsor wiki in the Store.

Step 4

Let the dot reach real systems. Move sweep connectors into OpenShell with read-only L7 policy and credential placeholders. Log every decision.

Step 5

Add a second workbench. Reconciliation and break management under the same dot, reusing the SDK, gate and approval patterns.
